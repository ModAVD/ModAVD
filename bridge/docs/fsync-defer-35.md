# 下载 fsync 延后（ModAVD#35 / PR #96）交接说明

2026-11-06 暂停。这份说明写给以后接手的人：目的、做了什么、试过什么和结果、怎么测、还要测什么。模块本身的设计说明在
[`bridge/README.md`](../README.md) 的「下载 fsync 延后（#35）」一节和 [`fsync_defer.cc`](../companion/jni/fsync_defer.cc) 的
文件头注释；测试工具在 [`tests/fsync_defer_device/`](../tests/fsync_defer_device/)。

## 一句话现状

延后 fsync 让明日方舟整包下载快约 8 倍，但**下载中途强杀（等于断电）后可能把资源包写坏**（active 强杀 8 次里 4 次），游戏解压报
「释放更新资源失败，错误号:302」，点重试也修不好。查到两条根因：第一条（改名比数据先落盘）已修住；第二条（补付和追加
同时进行，文件末尾留下半页 0）的修法在修后第一次强杀时又复现，但那一轮强杀重开后模块很可能没装上，修法其实没被测到。
按维护者的决定先暂停：**不合、不能默认开**。

## 目的

明日方舟（只有 arm64 代码、整个跑在转译层上）下载资源时，下载线程每写约 7 KB 就对 `*.downloading` 临时文件 fsync 一次，
每次 fsync 都要穿过 FUSE → ext4 → qcow2 → 宿主文件，在虚拟盘上真落盘，下载被卡在约 6–8 MB/s（#35）。把这些 fsync 延后、
按文件异步补一次真 fsync，下载就能跑到网络和解压的上限。

实测（同一台测试实例：6 GB / 4 核，ModAVD 0.38.0 / 0.38.1，明日方舟 2.7.91 未登录；每轮清掉已下资源从头下，取下载开始
20 s 后的 150 s 定窗，量文件目录 `du` 的增长 + 客体网卡收包）：

| 模式 | 下载速度 |
| --- | --- |
| off（模块不装，`modavd.fsync.defer=none`） | 5.4–7.6 MiB/s（4 轮） |
| observe（装过滤器、每次 fsync 照常真跑） | 5.7 MiB/s |
| active（延后） | 49.4、56.6、43.8 MiB/s（网络快的时段）；24–42 MiB/s（网络慢的时段，同一时段的 off 仍是 5–7） |

active 的绝对值随时段的网络（CDN）波动很大，各版本 gate 交替换装测过，没有哪个版本更慢。

## 做了什么（整体设计）

- **拦截点**：执行桥伴生库在名单内应用（默认只有明日方舟）的每个进程里装一个 seccomp-BPF 过滤器，对宿主的 `fsync`(74)
  和 `rename` / `renameat` / `renameat2` 返回 `SECCOMP_RET_USER_NOTIF`，其余（含 `fdatasync`、`close`）放行；同进程的监督线程
  从监听 fd 读通知、决定放行还是延后。拦的是转译之后最终那个宿主系统调用，游戏的 arm64 库一个字节都不改。
- **延后**（active）：已分类为匹配文件（路径匹配 `*/HGGameUpdate/HGDownload/*.downloading`、同 dev/ino、本进程、有补付槽）
  的 fsync，监督线程回 `val=0` 不 CONTINUE，内核直接给客体返回成功。认不准的一律放行真跑。
- **补付**：匹配时从游戏的 fd `dup` 一份自己的句柄；扫描线程每秒看一遍，欠账且距上次补付满 5 s 的文件用这个句柄补一次真 fsync
  （带魔数第二参，过滤器放行）。进程正常 `exit()` 时（atexit）把欠账立刻补完。
- **改名前补付**：active 下本进程每次改名前，先把所有欠账文件补付，再放行改名（根因 1 的修法）。
- **安全长度 + 启动截短**：每次补付前读文件长度 S0，fsync 成功后把 floor(S0, 4 KB) 记成文件的 xattr `user.modavd.fsync.safe`；
  应用启动、模块装上时，只要这个应用没有别的进程活着，就把带标记且比标记长的匹配文件截到标记长度，让游戏按长度重下
  （根因 2 的修法）。
- **只拦 fsync、放行 fdatasync**：下载只发 fsync，安卓自带的 SQLite 只发 fdatasync（实机核过），所以框架里的数据库不进陷阱。
- **观测**：每 60 s 一行 summary（logcat tag `ModAvdFsync`）：recv / real / other / foreign / rename / deferred / payback /
  rename_flush / xattr_err / repaired / recv_enoent / send_enoent / stuck 等。

## 试过的和结果（没成的也写）

- **拦截点**：Java 层钩子（`FileDescriptor.sync`）抓不到——下载用的是原生 fsync；钩转译器导入的 `syscall()` 也抓不到——
  转译器发客体系统调用走内联 syscall 指令。只有 seccomp 拦最终的宿主系统调用可行。
- **302 根因 1：改名比数据先落盘**（强杀轮次 k-active-4）。游戏下完一个约 400 MB 的包是「写 → fsync → 关 fd →
  `*.downloading` 改名成 `<uuid>`」，改完马上解压、解完删包（inotify 看到的顺序）。延后的最后几秒（扫描线程最多 5 s 补一次）
  还没落盘，改名先进了日志；断电后改了名的包名字、大小都对，尾部没落盘，游戏当成已下完 → 解压 CRC 失败，每次重试都一样。
  改名前补付修住了：修后那次强杀时正好有一个改名约 2 s、正在解压的包，重启后 211 个 zip 条目全对。
- **302 根因 2：补付和追加同时进行，文件末尾留下半页 0**（k1、k-active-101、k-active-201）。重开后续传完成的包只有一个 zip
  条目 CRC 错，它正好跨在重启时盘上文件的末尾；那里有一段 0（k-active-101：80172000–80175104，3104 字节）。盘上前缀和续传完
  的文件前缀逐字节一致：游戏按文件长度续传，这段 0 永远留在包里。机制：扫描线程替游戏补付（真 fsync）时，下载线程还在往
  同一个文件追加，ext4 把没写满的最后一页按旧末尾补 0 写下去，提交的长度却已是追加后的值，这页再写一次前断电就留下 0。
  游戏自己发的 fsync 不会和自己的追加同时进行，所以不延后时没有这个问题。
- **曾怀疑「下载进度记在 fdatasync 放行的数据库里、先于数据落盘」**：核过不成立。游戏的 `db_game_update` 只记客户端更新任务，
  资源下载按文件长度续传。
- **安全长度 + 启动截短的子进程误截**：模块拿到的是**包名**不是进程名，应用每个进程都一样；明日方舟下载期间反复拉起反作弊
  子进程，第一版（`4f67a62`）里它们一起来就把主进程正在写的文件截短，**没有强杀也报 302**。`0c47c8c` 改成「同 uid 没有别的
  进程活着才截」：正常下载 250 s，子进程 3 次都跳过，0 次误截、0 次解压错误。
- **为什么没用「定期放行游戏自己线程的 fsync」（SECCOMP_USER_NOTIF_FLAG_CONTINUE）代替扫描线程补付**：它能消掉补付和追加
  的竞争（真 fsync 发生在下载线程身上，它这时不追加），但客体的后台回写（ModAVD 管理器把 `dirty_expire_centisecs` /
  `dirty_writeback_centisecs` 设成 200 / 100）同样会和追加撞上，两次放行之间仍可能提交半页 0——窗口能缩到放行间隔以内，
  但不是零，所以还得配一个启动修复。这一轮只做了一种（xattr 截短），没有试 CONTINUE。
- **EINTR**：被拦的调用在内核里是可中断等待；处理函数不带 `SA_RESTART` 的信号会让它对客体返回 EINTR（真 ext4 fsync 不会），
  用 fsync 落盘的 SQLite 不重试 → `SQLITE_IOERR_FSYNC`；带 `SA_RESTART` 时内核自动重做，客体看不出来。实机探针复现了：
  不带 `SA_RESTART` 时 SQLite（DELETE 日志）800 次提交里 11–168 次 `SQLITE_IOERR_FSYNC`，带了 0 次，不装过滤器 0 次。
  放行 fdatasync 以后系统 SQLite 完全不进陷阱，同样条件 0 次错误。真下载里每轮约 100 万次通知，打断次数一直是 0。
  `SECCOMP_FILTER_FLAG_WAIT_KILLABLE_RECV`（Linux 5.19+，这台 6.1 内核认）只管监督线程收到通知之后那段，探针里加上后
  `send_enoent` 归 0，但总 EINTR 没变少（多数打断发生在收到之前），所以没用。打断次数 = `recv_enoent` + `send_enoent`。
- **画面卡顿不是 #96 的问题**：active 下每 150 s 约 10 次 0.4–1.3 s 的停顿（off 3–7 帧超过 100 ms）。查实是整个客体停住：
  客体里一个每 5 ms 醒一次的心跳线程同样停；宿主磁盘写延迟（中位 0.27 ms）和 CPU 正常；不是客体时钟跳（宿主 / 客体收到的
  空白一样长）；停掉游戏、客体里 `dd` 不带 fsync 狂写也一样停 310–781 ms。是模拟器 I/O 这一层在客体大量写盘时的问题，#96
  只是让同样的停顿集中在几分钟里（按每 GB 算反而更少）。
- **E 盘（宿主）USB 重置**：测试期间偶有 disk 153 / UASPStor 129，最多一分钟 7 条，记在结果里，和结论无关。

## 怎么测

工具和命令见 [`tests/fsync_defer_device/README.md`](../tests/fsync_defer_device/README.md)。要点：

- **游戏**：明日方舟。首次启动同意用户协议；客户端过时会自己下新整包（约 1.9 GB），`pm install -r` 装上；资源下载
  （「下载完整资源」约 12.8 GB + 默认中、日配音包）在登录前开始，不用登录。两个确认框用屏幕像素判断再点。
- **单测 + 变异**：`fsync-defer-test` 在实例上 ALL PASS；`make-mutants.ps1` 的 25 个变异每个都要 FAIL。
- **测速**：`dl-window.ps1` 每轮清资源、从头下，150 s 定窗；off / active 交替；先核 `current_clocksource` 是 `tsc`（开机后偶尔
  退成 hpet，那次作废）；记下宿主负载。
- **强杀**：`dl-kill.ps1` / `dl-killloop.ps1`：active 下从头下到约 2 GB → 不带 sync 的 `adb emu kill`（和断电等效：客体页缓存
  全丢）→ `modavd start` 重开 → 重开前拷下盘上下载目录里的全部文件、扫全 0 块 → 设回模式、启动游戏观察 150 s。
- **判 302**：游戏界面「释放更新资源失败，请重试，错误号:302」/ logcat 里 zip4j「crc verification failed」。坏包用 Python
  `zipfile` 逐项读，找到坏条目和偏移，再看它是否跨在重启时的文件末尾、附近有没有 0。
- **验收标准**（这一轮定的）：修好的版本强杀 10 次 0 次 302；再整包下完进标题页、退出再进没问题。偶发问题一种条件最多 10 次。

| off | 1 次 | 0 |

**注意**：三次出事的强杀（k-active-4、k-active-101、k-active-201）重开后的 logcat 里**一行 `ModAvdFsync` 都没有**（执行桥自己的
ModAvdNB / ModAvdGate 日志都在），也就是强杀重开后这一段 fsync 模块很可能没装上——修前那两轮不影响结论（数据是强杀前写坏
的），但 `0c47c8c` 的启动截短根本没跑，所以 k-active-201 不算对它的有效检验。整包下完进标题页、退出再进没做到这一步。

## 没解决的问题、已知风险

1. 强杀重开后 fsync 模块为什么没装上（硬杀前同一台实例上一直正常装上）。
2. 根因 2 的修法有没有效：要在模块确实装上的前提下重新强杀 10 次。
3. 启动截短的前提是「应用的第一个进程就是下载所在的主进程」；开机后若游戏别的组件先起来，就会跳过（不截，安全但修不了）。
4. 默认名单就是明日方舟，observe 也会装过滤器；痕迹：`Seccomp_filters` 1→2、`NoNewPrivs` 0→1、≥900 的 seccomp notify fd、
   2–3 个同名线程。登录态、反作弊、崩溃路径没在实机验过。
5. 截短改的是游戏自己的半截文件（只碰匹配 `*.downloading` 的、只截不加、只在下载开始前），依赖「游戏按文件长度续传」，
   换了游戏或游戏改了续传方式要重新核。
