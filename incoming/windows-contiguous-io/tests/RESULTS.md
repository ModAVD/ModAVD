# Windows 连续缓冲区 I/O 验证

日期：2026-11-06。补丁只调整 `block/file-win32.c` 内一个请求的缓冲区表示，保留原有同步完成、错误处理和 flush 路径。完整候选版本已完成构建、客体真实 fsync 测试，以及下述游戏观察。

## 完整候选构建与运行

使用 Clang 22.0.2、MSVC 14.51 和相同 Release 参数，分别构建了基线与候选版本的 `qemu-system-x86_64-headless`。两份源码工作区均干净，固定版本依赖和配置摘要一致。未同步整套 Android，也未下载系统镜像。

宿主为 Windows 11 Pro 26200、Intel Core i7-13700KF、约 32 GiB 内存、WD_BLACK SN850X 2000GB NVMe、GeForce RTX 4060 Ti。

候选版本增量编译时，构建规则通过原始 `wholearchive` 参数引用公共库，库变化未触发模拟器重新链接。这次旧 EXE 产物未用于测试；通过原构建目标重新链接后，核对了源码、编译命令、对象文件和 EXE。21 项运行产物中只有 headless EXE 不同。哈希、源码提交和构建参数见 [full-emulator-build.json](results/full-emulator-build.json)。

候选游戏测试使用已核对哈希的候选 EXE；客体写入对比每轮分别核对基线或候选 EXE。游戏使用独立测试实例，6 GiB 内存、4 vCPU、64 GiB 数据盘、1920×1080、60 FPS、headless 模式，没有登录账号。

候选测试的客体 Private DNS 设为 `off`，宿主代理、DNS 和路由未改动。这是测试条件，不属于补丁。

### 明日方舟下载中的写入等待

强杀恢复后另取三次只读快照，共 15.98 秒。两个窗口实际接收为 11.06、11.40 MiB/s，两个 CDN 连接始终各有约 5.4 MB 接收队列。游戏工作线程在三次快照中两次等待 `jbd2_log_wait_commit`。客体 vdc 写入约 65.9–67.1 MiB/s，约 4,300–4,400 写 IOPS；游戏 CPU 约占 0.71 个核。

这些现场更支持客户端消费数据后的写入、日志提交存在限制，不能解释为纯 CPU 解包瓶颈。ext4 日志提交有实际落盘语义，不能提前返回成功来消除等待；见 [内核日志说明](https://docs.kernel.org/filesystems/ext4/journal.html)。虚拟盘报告的 busy 约 99% 只属于该设备的 I/O 统计，不能据此认定宿主物理 SSD 带宽已满；见 [I/O 统计定义](https://docs.kernel.org/admin-guide/iostats.html)。

证据见 [ark-download-layer.json](results/ark-download-layer.json)。网络、磁盘和 PSI 均为整个客体的计数；没有函数级剖析，尚不能拆分 fsync、校验、流式解压等具体耗时。

## 客体写入与真实 fsync

在两台相同配置的新实例上交替运行完整编译的基线和候选版本。每次冷启动后静置 30 秒，依次用 1、4 个线程运行 10 秒。[syncbench.cc](syncbench.cc) 每个线程追加 7,168 字节后立即执行真实 `fsync`，只写自己的临时文件。每轮核对实际 QEMU 哈希、加载模块、客体时钟与回写设置；没有游戏或编译任务并行运行。

下表使用 B2/C2、B3/C3、B4/C4 三组相同冷启动条件的正式样本。最初 B1/C1 的热身时序不一致，保留为探索数据并排除。全部 20 个热身、探索和正式样本均为零错误，原始数据和控制条件见 [native-fsync.json](results/native-fsync.json)。

| 线程 | 基线三轮 MiB/s | 候选三轮 MiB/s | 中位数变化 |
| ---: | --- | --- | ---: |
| 1 | 18.0714 / 20.1835 / 17.0798 | 18.3831 / 17.4975 / 20.0440 | +1.72% |
| 4 | 41.6205 / 49.6038 / 43.6027 | 53.0153 / 50.3754 / 51.8848 | +18.99% |

单线程逐对变化为 -13.3% 至 +17.4%，没有稳定提升。四线程三组均较高，逐对变化为 +1.56% 至 +27.38%，中位数从 43.6027 到 51.8848 MiB/s。这是同一宿主、两台新实例上的短窗口写入测试，不能换算成游戏下载提速或断电持久性结论。

## Windows API 用例与微基准

Windows x64、MSVC 14.51、Intel Core i7-13700KF。测试直接提取修改前后的实际函数，用适配类型编译后调用真实 Windows 文件 API。

- 34 项功能用例通过，包含内容独立读回、4 GiB 以上偏移、非缓存 I/O、EOF、短写、I/O 错误、内存分配失败和 flush 错误。真实 I/O 用例最大请求为 1 MiB，非缓存用例为 8 KiB。
- 从已有 Git 对象重新回放 mas38 的 95 个补丁，树与发布记录一致。新补丁可以原样 `git am --keep-cr`，应用后同样通过 34 项用例。
- 仓库的 11 组发布补丁全部回放通过。使用原版 `scripts/checks.py patches`，通过 Git URL 映射读取已有本地仓库，并设置 `GIT_ALLOW_PROTOCOL=file`，没有下载 AOSP。
- 元数据与公开隐私规则检查通过。

微基准交替运行修改前后版本，共六轮，比较中位耗时。相同缓存文件范围被重复读写，末尾 flush 不计入计时。

| 缓冲区 | 请求大小 | 读耗时变化 | 写耗时变化 |
| --- | ---: | ---: | ---: |
| 连续 | 8 KiB | -12.1% | -5.6% |
| 连续 | 16 KiB | -14.1% | -8.9% |
| 连续 | 64 KiB | -34.9% | -25.1% |
| 连续 | 1 MiB | -92.4% | -95.3% |
| 分散 | 8 KiB | +5.4% | +0.9% |
| 分散 | 16 KiB | -0.1% | -1.2% |
| 分散 | 64 KiB | -0.2% | +0.5% |

连续 16 KiB 请求省去临时缓冲区分配和复制；测试中按 256 × 4 KiB 分段的连续 1 MiB 请求从 256 次 Windows 调用减为一次。分散 8 KiB 读的这一轮结果较慢，不能宣称所有情况都无回退。

原始样本在 [benchmark.csv](results/benchmark.csv)，汇总与源码哈希在 [results.json](results/results.json)，功能用例输出在 [checks.txt](results/checks.txt)。这些数据不包括 QEMU 线程调度、qcow2、客体文件系统和网络，只说明该宿主函数的表现。

### 发布版强杀后的低速诊断

在发布版明日方舟下载中结束测试 QEMU，未先执行 guest sync。冷启动后游戏可以继续处理资源，但实际网络接收降到约 0.154 MiB/s。同一客体的独立小块写入加真实 fsync 探针仍为 13.62 MiB/s；游戏的两个下载连接接收队列为空，下载线程在等待网络。这与候选版本中接收队列持续积压的现场不同。

客体 DNS 将 `ak.hycdn.cn` 解析到 `43.109.5.15` 一带的节点，宿主解析得到不同节点。对同一个官方资源做两轮交替的 1 MiB HTTP Range 请求，所有响应均为 206、TLS 校验成功、内容 SHA-256 一致。原节点实测约 0.066–0.158 MB/s，另外两个节点约 8.1–11.9 MB/s。

仅把独立测试客体的 `private_dns_mode` 从未设置改成 `off`，再重启一次游戏应用，连接切换到 `60.188.140.124`。之后 60 秒实际游戏网络接收恢复到 10.91 MiB/s，客体没有再次重启。宿主 v2rayN、DNS 和路由未改动。这项临时测试环境调整没有包含在补丁中；恢复原设置的命令是 `settings delete global private_dns_mode`。

证据见 [network-diagnosis.json](results/network-diagnosis.json)。这说明本次极低下载速度来自所选 CDN 节点或到该节点的链路，不证明节点的物理位置，也尚未定位 DNS 与 TUN 的具体上游交互。

同一轮随后完成资源处理，进入无下载进度或错误提示的 START 标题页。同步数据并重新启动游戏后，先显示资源完整性检查，随后回到带语音配置提示的标题页，未见重新下载或错误提示。结果见 [arknights-crash-baseline.json](results/arknights-crash-baseline.json)。发布版也只做了一次强杀，未独立扫描所有资源 CRC。

## 验证范围

完整候选构建、真实 fsync 测试和三款游戏所选的登录前资源流程已取得上述结果。没有登录账号或验证登录后的游戏流程；未覆盖其他存储后端和所有请求大小。

候选明日方舟的一次强杀恢复不能证明普遍的断电持久性，也不能替代 #96 active 模式的验证。连续缓冲区在真实游戏请求中的命中比例尚未测量；没有完成同条件的游戏 A/B 测速，不能宣称已解决 #35 的下载速度目标。
