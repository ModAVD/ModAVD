# ModAVD release framework

[简体中文](README.md) | **English**

<!-- README.md and README.en.md match section by section: if you change one, change the other in the same PR. -->

The entry points run on PowerShell 7 and the helper code uses only the Python 3.12 standard library; you need Git and 7-Zip, and to create a draft also a logged-in `gh`.
The release checklist is [RELEASING.en.md](../../RELEASING.en.md) in the repository root; this page describes the tools themselves.

Paths that depend on the machine (source tree, temp directory, external inputs) are always arguments; what is not given is taken from the local config, see [tools/README.en.md](../README.en.md) and [tools/local.example.psd1](../local.example.psd1). If neither has it, it is an error; no default is guessed.

## Version numbers

The public version `X.Y.Z` is given with `-Version`, and Y does not have to equal the emulator build number: Y goes up only when the emulator itself is rebuilt; if it was not rebuilt (only components changed, or the package was only repackaged), only Z goes up. For example, after 0.40.1, a release that changes only the manager and the capture library is 0.40.2.
From 0.42, the build number is the version of the rebuild it belongs to; the argument is written `-Build 0.42` (`0.42.0` is also accepted), and on disk it is always three parts: `sdk-0.42.0`, `Pkg.BuildId=0.42.0`, the patch directory `qemu/0.42.0`, `manifest-0.42.0.xml`; `build` in `modavd-manifest.json`, in the machine-readable line of the notes and in every entry of `changelog.json` is the string `"0.42.0"` ([#219](https://github.com/ModAVD/ModAVD/issues/219)). 0.41 and earlier use mas-N (`sdk-masN`, `Pkg.BuildId=mas-N`, the patch directory `qemu/masN`, and `build` is the integer N): directories, manifests and entries that were already released are not renamed, and the checks accept both; `-Build masN` is kept only for rebuilding those historical builds. The new form starts at 0.42, and `-Build 0.41` and earlier is rejected.
The tag is `v<version>` and the title is `ModAVD 0.41.0`; the upstream version (`Pkg.Revision`, such as 37.2.10) goes into the first sentence of the notes, "ModAVD 0.40.2, built on Google AOSP Android Emulator 37.2.10"; the build number is recorded only in the manifest and in `build` of the machine-readable line, and is not written in the body of the notes.

0.40 and earlier follow the old rule: in the version `0.<N>.<P>`, N is the build number and P counts the times the package was only repackaged; without `-Version`, `release.ps1` still computes it this way (the old name `v37.2.10-masN` of mas30 and mas32 counts as `0.N.0`, and they can only be repackaged with `-Patch 1` or higher). The checks still accept those old entries.

## Build

```powershell
pwsh -NoProfile -File tools/build/build-sdk.ps1 -Build 0.42 -WhatIf
```

It compiles for real only after `-WhatIf` is removed. `-EmuSrc` (local config `EmuSrc`) is the AOSP emulator source tree; `-Jobs` defaults to 12, range 1-16; `-Python` defaults to `MODAVD_PYTHON`, then the local config `Python`, then `python` on PATH; `-LogRoot` defaults to `<TempRoot>\build-sdk`; `-MinFreeGB` defaults to 120 (on the drive where the source tree really is; a directory junction is followed).
It refuses to run when the target `<EmuSrc>\sdk-0.42.0` already exists; it does not use clean / removeleftover and runs no delete command. The source must be committed, and the output is installed only if the commit snapshots before and after the build are the same.
The output is copied to `sdk-0.42.0/emulator` and `Pkg.BuildId` is written as `0.42.0` (the old form such as `-Build mas34` gives `sdk-mas34` and `mas-34`); `build-info.json` is saved next to it so that the release entry can determine the matching source.

The three payload files of the arm64 execution bridge (`emulator/resources/modavd/`) are not AOSP build output; `tools/gate/stage-payload.ps1` puts them into the SDK tree separately: `build-sdk.ps1` runs a read-only `-CheckOnly` once before `ShouldProcess` (`-WhatIf` checks too), and puts them in for real after robocopy and after `source.properties` is written.
`-GatePayload <frozen directory>` names where the payload comes from; if it is not given, the order of `stage-payload.ps1` is followed.
The payload hashes are pinned in `tools/gate/payload.SHA256SUMS.txt`; after you rebuild the payload, run `stage-payload.ps1 -UpdateSums` first to pin it again, otherwise packaging stops at once. For how it works see [tools/gate/README.en.md](../gate/README.en.md).

## External inputs

These are not in the repository and must be prepared before the release (the key names in the local config are in brackets):

| Input | What it is, where it comes from |
| --- | --- |
| SDK (`-Sdk`) | `sdk-0.N.0` built by `build-sdk.ps1` (`sdk-masN` for old builds), with `build-info.json` |
| Source tree (`EmuSrc`) | The AOSP emulator source tree that built this SDK. Patches are exported from the commit recorded in `build-info.json`, and changed source projects are `git archive`d from here |
| Source baseline (`Baseline`) | Unchanged source archives are reused directly, and each is checked against the frozen hash in `config/mas30.SHA256SUMS.txt`. You can make it from the source package of the mas30 Release: put the contents of the folder in `ModAVD-37.2.10-mas30-sources.zip` into `<Baseline>\source\`, and copy `release/37.2.10-mas30.sources.SHA256SUMS.txt` in the repository to `<Baseline>\SHA256SUMS-sources.txt` (this way was derived from the code and has not yet been followed from scratch) |
| Notices and licenses (`LicensePackage`) | The reviewed `LICENSES\` (`NOTICE.txt`, `NOTICE.csv`, the full text of each license). The pre-check requires `LICENSES\AGPL-3.0.txt` to be there, and its SHA-256 after line endings are normalized to LF to be `AGPL_SHA256` in `release_tools.py` (that is `package/LICENSE`), otherwise it stops. For now it is only on the maintainer's machine |
| Desktop APK (`LauncherApk`) | The launcher under `components\`; its file name and SHA-256 are pinned in `config/components.SHA256SUMS.txt` |
| Manager (`-Manager`) | The ModAVDManager Release attachment `ModAVDManager-<version>-win-x64.zip` |
| Host IME (`-ImeApk`) | The ModAVDHostIME Release attachment `modavd-ime.apk`; if not given, it is not included |
| Capture library (`-ExtrasDll`) | The ModAVDExtras Release attachment `modavd_extras.dll`, placed as `extras\modavd_extras.dll`; it is in every package and must be given |
| MuMu compatibility shell (`-MumuShim`) | The Release attachment `external_renderer_ipc.dll` of the same ModAVDExtras version, placed as `mumu-shim\shell\sdk\external_renderer_ipc.dll`; given together with `-ExtrasDll`, and must be given |
| Clones of the three public repositories (`ManagerRepo`, `ImeRepo`, `ExtrasRepo`) | Only tags are read, whichever branch is checked out: run `git fetch upstream --tags` first |
| Private privacy rules (`PrivateRules`) | The maintainer's own `privacy-private-rules.json`, kept outside the repository and never committed (see "Shared checks and privacy rules" below) |

## Release

Neither "What's changed" (更新内容) nor the English "What's new" of the notes is written by hand. For a change users can see, its own PR carries a note file (`changelog.d/<name>.<feat|fix|change|remove>.md`, two lines: Chinese, then English; for how to write it see [changelog.d/README.md](../../changelog.d/README.md)); at release time, the files added since the last release are collected into `config/changelog.json` ([#216](https://github.com/ModAVD/ModAVD/issues/216), [#261](https://github.com/ModAVD/ModAVD/issues/261)):

```powershell
pwsh -NoProfile -File tools/pubrel/collect-changelog.ps1 -Build 0.42 -Version 0.42.0 [-Note "更新前先把实例都关机" -NoteEn "Shut down the instances before updating"] [-MinAutoMas 5.9.0-beta.1]
```

- It reads the `changelog.d` of four repositories: for ModAVD it reads HEAD of the release clone; for the manager, the capture library and the IME it reads the head of each one's `upstream` `release/<X>.<Y>` (the paths come from `-ManagerRepo`, `-ExtrasRepo`, `-ImeRepo` or the local config; run `git fetch upstream --tags` first). A component without this release branch counts as not repackaged in this release and gives no entry; so does the manager or the capture library when the version written at the head of that branch (`internal/buildinfo/buildinfo.go`, `CMakeLists.txt`) is not this release's (a repackaged component takes this release's version). The IME writes no version: it has a release branch only when it is repackaged.
- "Newly added" means a file that this commit has and the last release does not. The last release is found by version, not by which commit comes before which ([#277](https://github.com/ModAVD/ModAVD/issues/277)): only tags that are exactly `vX.Y.Z` count (not ModAVD's early tags like `v37.2.10-mas32`, nor any tag with a suffix), and it is the highest one below this release; for the IME, whose version is not known, the highest one that is not on this commit. A release commit is only on `release/<X>.<Y>`, and with squash merges only it never comes back to main, so the next release branch, cut from main, does not reach its tag: looking for the nearest tag going back would miss it. A tag above the chosen last release that is not on this commit (this version was already released from another commit, or a newer one exists) stops it with an error instead of comparing against the wrong release. If the Chinese line of an already released file was changed, it is an error: put later changes in a new file. Adding or changing only its English line is fine (files released in 0.43 and earlier had only the Chinese line and got the English one later).
- The type in the file name is the category: `feat` added, `fix` fixed, `change` changed, `remove` removed. The Chinese entry is the first line of the file, with the PR that added the file (the number at the end of the merge commit title) written as `(#N)` or `(ModAVD/ModAVDManager#N)`; a line that already ends with an issue or PR number gets nothing appended. The English entry is the second line; without a number of its own it gets the same one as the Chinese line.
- A file that does not qualify (wrong name, not exactly two lines, a first line without Chinese or over 60 characters, a second line with Chinese characters or over 120 characters, contains `--`) is reported all at once; fix the files and run again. ModAVD's own `changelog.d` is also checked in `checks.py metadata` in CI.
- Each repository also lists the commits since the last release that carry no note file, so you can check by eye that no user-visible change was missed.
- A "note" is written by hand with `-Note`, only for what the user has to do in this release, each `-Note` with its English `-NoteEn` in the same order; it is kept when you collect again. If `-MinAutoMas` is not given, the previous one is kept, and `none` means no requirement; it goes only into the machine-readable comment on the first line and is not written in the body of the notes. For a version whose build number is `0.N.0`, `min_automas` must be at least `5.9.0-beta.1`: AUTO-MAS 5.8.0 and earlier look up the internal-test package version by `Pkg.BuildId=mas-N` before boot, and block the boot if they cannot recognize `0.N.0`; a lower value stops both the collecting and the pre-check.
- What is written is this release's entry at the top of `changelog.json`, `{"version": "v0.42.0", "build": "0.42.0", "min_automas": "5.9.0-beta.1", "changes": {"修复": ["…"]}, "changes_en": {"Fixed": ["…"]}}` (the entries of 0.41 and earlier have an integer such as `"build": 41`, and stay as they are; the entries of 0.43 and earlier have no `changes_en` and also stay as they are, only the release being made must have it); running again replaces the whole entry. The English categories are New, Changed, Fixed, Removed and Notes, one for each Chinese one, with the same number of items. `changes_en` does not go into the machine-readable comment. The machine-readable comment on the first line carries up to 10 entries from the top of `changelog.json`, for AUTO-MAS to merge and show when it skips versions; if the whole line is over 8000 characters the pre-check stops, and then the only way is to delete the oldest entries or shorten the old ones.

Apart from "What's changed", the notice has only one opening line: the upstream version it is based on, the version of each component (the ones repackaged in this release are marked) and a link to the docs site. How to update, known issues and how the regression was tested are not written in the notice; if this release has something the user has to do, write it as one "note" with `-Note`. Below the separator line and before the download table comes the English "What's new": the same opening line and the same categories in English. It is only on the GitHub release page, is not synced to MirrorChyan and does not count towards the 4000 characters.

When the manager, the capture library or the IME was repackaged in this release, its version is this release's ModAVD version, and one that was not repackaged is left alone; a component that has no tag yet and whose version does not match makes the pre-check stop. Their own repositories' Release notes are not written by hand either; they are generated on the component's release branch:

```powershell
python -I tools/pubrel/release_tools.py component-notes --component manager --version 0.41.1 --sums release/0.41.1.SHA256SUMS.txt --notes-output release/0.41.1.md
```

`--component` is `manager`, `extras` or `ime`; what is generated is one sentence each in Chinese and English, "Released with ModAVD 0.41.1", plus the checksum table.

After collecting, check the notice length first, with no SDK and no packaging:

```powershell
python -I tools/pubrel/release_tools.py notes-budget --build 0.42 --version 0.42.0 [--sdk <SDK root>]
```

It reports the length of the machine-readable line (limit 8000 characters, carrying the changes of up to 10 entries from the top of `changelog.json`, old entries included) and of the notice above the separator line (limit 4000 characters); over the limit it is an error that says where to cut, and above 90% it warns. Without `--sdk`, the upstream version is estimated as `99.99.99`, a character or two longer than the real one. The pre-check of `release.ps1` checks again with the same algorithm, and stops before packaging if it is over.

Then check this release's NOTICE, the component sources and the licenses; run the pre-release regression on a test machine ([ModAVDE2E](https://github.com/ModAVD/ModAVDE2E)), and keep the results to yourself, not in the notice.

```powershell
pwsh -NoProfile -File tools/pubrel/release.ps1 -Build 0.42 -Version 0.42.0 -Sdk <SDK root> -Manager <downloaded ModAVDManager-0.3.0-win-x64.zip> -ImeApk <downloaded modavd-ime.apk> -ExtrasDll <downloaded modavd_extras.dll> -MumuShim <downloaded external_renderer_ipc.dll>
```

By default it generates only the local output and the privacy report, into `<TempRoot>\pubrel\0.42.0-v0.42.0`.

The manager, the IME, the capture library, the execution bridge source and the bundled script all come from public repositories: the manager, the IME and the capture library use the attachments of their own Releases (for a manager or capture library with no tag yet, see the next section), and the bundled script and the execution bridge source come from `package/` and `bridge/` at the current commit of the release clone (`-Repository`, by default the clone this tool lives in).
Before releasing, update the release clone to the ModAVD release branch `release/<X>.<Y>` (the first two parts of the version, for example 0.41.x is `release/0.41`; see "Release branch" in [RELEASING.en.md](../../RELEASING.en.md)), and run `git fetch upstream --tags` in the three clones `ManagerRepo`, `ImeRepo` and `ExtrasRepo`.

### When a component has no tag yet

The manager and the capture library do not have to be released first. Once their release-preparation commit (version, `release/<version>.md`, `release/<version>.SHA256SUMS.txt`) is merged into each repository's `release/<X>.<Y>` (the first two parts of this ModAVD version), packaging can go ahead:

- If the tag `v<version>` is there, it is checked against the tag, as before.
- If the tag is not there, the head of that repository's `upstream` `release/<X>.<Y>` is used (run `git fetch upstream` first): the version at that commit must be this release (for the manager look at `internal/buildinfo/buildinfo.go`, for the capture library at `CMakeLists.txt`), and the files given in must match `release/<version>.SHA256SUMS.txt` at that commit. The output of the pre-check and of assembling says "NOT TAGGED YET" and the commit that was taken.
- For `-Manager`, give a package built on this machine from that commit (`build.ps1` of ModAVDManager with `mkzip`; the same source gives the same bytes); for `-ExtrasDll` and `-MumuShim`, give the two DLLs from the CI output `windows-libs` of that commit (a different MSVC gives different bytes, so a DLL built on this machine will not match).
- The package records the version and the commit, and `SOURCES.txt` and `modavd-src.tar.xz` are the same whether tagged or not. The regression uses exactly this output; at publishing, first put the tag on the recorded commit, and do not repackage.
- `-DraftRelease` accepts only a package whose components all have tags.

The IME does not take this route: it needs the official signing on this machine, so release it first through its own process.

### Release PR and the two workflows on GitHub

Packaging, the full scan with the private rules, the regression before release and creating the draft with its attachments are still done on this machine; checking the draft and closing issues are done by GitHub Actions ([#134](https://github.com/ModAVD/ModAVD/issues/134)). For this, the release PR carries two machine-readable things, both generated by `release-pr.ps1` from the release plan (a `.psd1` on the maintainer's machine, with `Version`, `Manager`, `Issues` and `ReviewedHead`):

```powershell
# Write release/<version>.issues.json, which goes into the release PR together with the release commit
pwsh -NoProfile -File tools/pubrel/release-pr.ps1 -PlanFile <plan.psd1> [-Repository <release clone>]
# After the review, put ReviewedHead into the plan, write the Reviewed-Head line into the PR body file, then gh pr edit <number> --body-file <file>
pwsh -NoProfile -File tools/pubrel/release-pr.ps1 -PlanFile <plan.psd1> -BodyFile <PR body.md>
```

- `release/<version>.issues.json`: `{"version": "0.42.0", "manager": "0.42.0", "issues": [{"issue": 103, "prs": ["ModAVDManager#54"], "kind": "close", "note": ""}]}`.
  `prs` is written as "repository#number" or "repository@commit"; an emulator source patch has no PR, so leave it empty and write which patch it is in `note`; `kind` is `close` (close it and attach the release link), `comment` (already closed, add one comment "released in"), or `keep` (post `note` as a comment and do not close). Every issue with `!pending-release` must be written in. The format is checked by `load_issues` in `release_ci.py`, and a mistake is reported at generation time.
- A line of its own in the PR body, `Reviewed-Head: <40-character commit>`, exactly one line, naming the head that was reviewed. If the PR gets new commits after the review, review again and rewrite this line.

The two workflows (the checking logic is all in `release_ci.py`, and its unit test `test_release_ci.py` runs in `check.yml`):

- `verify-release.yml`: trigger it by hand after the draft is made, `gh workflow run verify-release.yml --repo ModAVD/ModAVD -f version=<version>`. On GitHub's machines it downloads the draft's attachments and computes the SHA-256, and checks that: the attachments are exactly the two zips and `SHA256SUMS.txt`, and they match `release/<version>.SHA256SUMS.txt` at the release commit (the target of the draft, which must be on `release/0.<N>`; if the tag already exists it must point at it), and the digests that GitHub recorded are the same too; the Release title and notes match (`release/<version>.md`); there is exactly one release PR that was merged into this commit and into `release/0.<N>`, the `Reviewed-Head` in its body is a commit of this PR, and its tree is the same as the merge commit's. Publish only after it passes. A draft is visible only to a token that can write repository content, so the downloading job has `contents: write`; it does not check out or run code from the repository, uses only `gh` and `sha256sum`, and hands the hashes to a read-only checking job.
- `close-released-issues.yml`: runs by itself when the release is published on the web page (`release: published`), and can be rerun with `gh workflow run close-released-issues.yml --repo ModAVD/ModAVD -f version=<version>`. It uses only `GITHUB_TOKEN` (`issues: write`, everything else read-only). It reads `release/<version>.issues.json` at the commit the tag points at, and checks the PR that fixes each issue: a ModAVDManager PR's merge commit must be in the tag `v<manager>`; a ModAVD one must be an ancestor of the release commit (when the merge commit GitHub recorded is not on main because main was rewritten, it uses instead the one commit on main whose title ends with " (#number)" and that has the same tree, and skips the issue if there is not exactly one); for ModAVDE2E and ModAVDHostIME, being merged is enough; for "repository@commit" it checks that commit directly. For each one that passes, it closes or comments according to `kind` (a comment carries the link to the release page) and removes `!pending-release`; one that fails is left alone with its label and listed in the job summary, to be checked again in the next release. A rerun does only what is not done yet: it does not comment again where a comment already has the release link, and it does not remove the label when closing or commenting failed. What fires at publish time is this file at the commit the tag points at: a release branch cut before it was merged into main will not run it at publish time, and you have to trigger it by hand.

Pushing `release/0.<N>` and the tags of the three source repositories (ModAVDQemu, ModAVDGfxstream, ModAVDCrashpad) and changing the default branch need credentials that can write across repositories, and are not in CI yet; they are still done on this machine.

The output (taking `0.33.0` as an example):

- The main package `ModAVD-0.33.0-win-x64.zip`, with **no outer folder**: the package root is the ModAVD root folder. MirrorChyan compares files by path, and an outer folder carrying the version would make an incremental update equal to a full one (there is no separate `-update.zip` any more). A user who uses "Extract all" or 7-Zip "Extract to <package name>\" gets a folder with the same name. The file name carries the platform, because there may be a `linux-x64` later; the platform is written in `PLATFORM` in `release_tools.py` and in `release.ps1`.
- The package root has `modavd-manifest.json`: version, build number, upstream version, platform, minimum AUTO-MAS version, and the size and SHA-256 of every other file in the package. `verify-zip` checks that the main package matches the assembled directory file by file (an outer folder is an error) and that the manifest corresponds one to one with the files.
- The source archive `ModAVD-0.33.0-sources.zip` (platform-independent, with no platform in the name), made with 7-Zip `-tzip -mx0 -mcu=on`, with an outer folder of the same name. The internal source archives keep their original file names and bytes; an internal `SHA256SUMS.txt` is added.
- The outer `SHA256SUMS.txt` lists only the two ZIPs, the main package and the source archive.
- `release-notes.md`: a machine-readable comment on the first line, then the update notice (one line with each component's version, and what changed), then the separator line `<!-- modavd:github-only -->`; below it are the English "What's new" (the same opening line and changes), the download table and the source notes. The part above the separator line is in Chinese only, is synced to MirrorChyan and shown in AUTO-MAS, is limited to 4000 characters, and must not contain hashes.
- `release-assets.json` records the sizes and hashes for the repository CI to use.
- `patches/`: the patches that go into the release commit. `series.json` and `BASE.md` are the two files from the release clone (`-Repository`) plus this release, and overwrite the ones in the repository:
  - A series whose repository, base and branch head are all the same as a published one reuses that directory (for example Crashpad stays `crashpad/module-version22`), and no new directory is added; its export is put in `work/patches-reused/` for the replay and the incoming check, not in `patches/`.
  - The others are new directories (`patches/<repository>/<build>/`, such as `qemu/0.42.0` from 0.42 and `qemu/masN` before): one entry is added at the top of `series.json`; one row is added to the version table of `BASE.md` (for another release of the same build, such as a repackaging, find the row by the build number and only add "; <version> is the same"), one row is added to the directory table above the old row of the same repository, and one sentence is added to the explanation below the directory table (which first patches are the same as the previous directory and from which one on they are new, computed by patch-id).
  - The license of a new patch and what it does can only be written by a person, so they are left as "to fill before release": fill them in and then commit, because `checks.py metadata` fails when it sees them. The license table below the version table and the replay example are also edited by hand when needed.
  - If the release clone already has this release added (running it again), it is not added twice. `logs/patch-dirs.json` records which directory each repository uses in this release and whether it is new.

`config/sdk-inventory.csv` is the reviewed packaging policy: for now the SDK file set is fixed, with 103 files removed. A new SDK that adds or removes files stops it, and the policy must be reviewed and updated first.
The three rows under `resources/modavd/` are our own arm64 execution bridge payload (AGPL-3.0-or-later), which `tools/gate/stage-payload.ps1` puts into the SDK tree; they are under `sdk/emulator`, so the internal-test rule "ship only `sdk\emulator`" needs no change. `tools/modavd-bridge.ps1` in the package (install / uninstall / verify the execution bridge) is taken byte for byte from `package/` of the release clone by commit (there `package/** -text`, and what is stored is the bytes in the package). The packages of 0.38.1 and earlier also had three .bat files and `fetch-components.ps1`, `collect-info.ps1` and `report-config.ps1`; from 0.38.2 the manager and the command line do these things and the package no longer has them (ModAVD/ModAVD#45); when upgrading with `modavd update`, a package-root file that the old manifest has and the new package does not is deleted.

Since 0.36.0 the package also has `ModAVD.exe` (the manager) and `tools/modavd.exe` (command line, MCP), taken from the Release package named by `-Manager` (ModAVDManager's own release process reproduces the build and checks it).

Things newly released, or no longer released, after the NOTICE reviewed in P3 are applied by assemble at the anchors: the program icon entry loses the wording about fan work and is renamed "ModAVD program icon" (`ICON_NOTICE_EDITS`); files no longer released are taken out of existing entries (`NOTICE_GONE_FILES`; from 0.40.1 the package no longer carries `说明.txt`, for usage see the manager and the docs site, and a whole-package update deletes it according to the old manifest); newly released files are added (`NOTICE_MORE_FILES`); and the entries of `config/notice-additions.txt` / `.csv` are added at the end of Part 2 (the execution bridge payload, the two modavd exe files, the BSD-3 notice of the Go runtime, with the Go version taken from go.mod at the manager tag; since 0.39.0 also the LGPL-3.0-or-later notice of the capture library); if an anchor or the original text is not found, or found in more than one place, it stops.
After this, it is checked in both directions: every file below the package root (except `sdk/`) and every file in `sdk/emulator/resources/modavd/` must have an entry in NOTICE.txt (license full texts excepted); every `(package root)` file in NOTICE.txt must be in the package. Packaging stops if a file is added to the package without an entry, or a file is taken out without changing the entry.

The source archive has one more file, `modavd-src.tar.xz` (called `modavd-src-<commit>.tar.xz` at 0.36.0): the plain `git archive` of each public repository; `ModAVDManager/` is the tag of `-Manager`, `ModAVDHostIME/` is the tag that `-ImeApk` matches, `ModAVDExtras/` is the tag that `-ExtrasDll` matches (the commit at the head of the release branch when the manager and the capture library have no tag yet), and `ModAVD/bridge/` is `bridge/` at the current commit of the release clone.
The archive root also has `LICENSE` (`package/LICENSE`, the full AGPL-3.0 text, checked against `AGPL_SHA256`) and `NOTICE` (`config/own-sources-NOTICE.txt`: which parts are our own, the exceptions and the third-party parts, and where each part is publicly available) of this repository's HEAD (`OWN_SOURCES_ROOT`); timestamps and owners follow `git archive`, and the two root files take the latest commit time of the three commits, so it is reproducible. Section 6 of `SOURCES.txt` states the tag and commit of each part.
The pre-check stops if `LICENSE` or `NOTICE` has uncommitted changes. The bundled script is itself source and is shipped as it is in the main package, not in this archive.

Our own parts (the manager and the command line, the execution bridge, the host IME, the bundled script) are released under AGPL-3.0-or-later, and are publicly available at:
the manager https://github.com/ModAVD/ModAVDManager, the IME https://github.com/ModAVD/ModAVDHostIME, the bundled script (`modavd-bridge.ps1`, which installs the execution bridge) https://github.com/ModAVD/ModAVD/tree/main/package,
the execution bridge https://github.com/ModAVD/ModAVD/tree/main/bridge.

When 24 source projects change, they are `git archive`d again; a change in other manifest projects (especially prebuilts) stops it, and the matching source and NOTICE must be reviewed again.

## Shared checks and privacy rules

`checks.py`, `privacy.py` and the allowlist `privacy-allowlist.json` exist only once, in `scripts/` of the repository: the public CI and the release entry use the same ones.

- `checks.py metadata --root <public repository>` checks the Release tables, the two layers of checksum tables, the size records and `.gitattributes`; for notes since 0.33.0 it also checks the machine-readable line, the separator line and the notice length;
  `patches --root <public repository> --work <fresh temp directory>` shallow-fetches the base straight from AOSP, replays the three series and compares the final source trees.
- `privacy.py <public repository>` scans the files Git tracks; the release entry uses the same module to scan the main package, the patches, all members of the source archive and the metadata.
- The repository holds only the general rules (`PUBLIC_RULES`). The rules that name private information (real names, private e-mail addresses, host names, local directories) are in the maintainer's own `privacy-private-rules.json`, **kept outside the repository and never committed**: load it with the environment variable `MODAVD_PRIVATE_RULES`, `privacy.py --private-rules <file>` or `privacy.use_rules(<file>)`; pointing at a file that does not exist is an error. The public CI runs without it; step 8 of the release stops if it was not loaded.

Step 8 of the release caches the clean results of scanned files by file hash (`cached_privacy_scan` in `release_tools.py`; `privacy.py` itself is unchanged):

- A file whose content (SHA-256) and location are the same as when it was last scanned (with the outer `ModAVD-<version>-<platform>/` of the main package removed, so a file unchanged since the last release counts too) is not scanned again; source archives are counted by the hash of the whole file, and an unchanged archive need not even be unpacked.
- Any change of the scanner's code, the rules (public and private), the major version of Python or the Unicode version (which strings count as printable and get checked depends on the Unicode library) voids the whole cache. The allowlist is not in it: each cache entry records the exceptions it used, and on a hit each one is checked again against the current allowlist, so a withdrawn exception makes the files that used it be scanned again and fail as usual.
- Only clean results are cached; a file with a failure is scanned every time. The report (`logs/privacy.json`) is the same as without the cache, with one more `cache` field recording the hits and how many were rescanned.
- Each time, the cache keeps only the entries used in this round, following the latest release; if the file is damaged the whole cache is dropped and started again, and if a single entry has a wrong format only that entry is dropped and that file is scanned again.
- The cache is an input on this machine, and writing a "clean" record in the right format would make a file skip the scan. So **the round that really uploads (`release.ps1 -DraftRelease`) does not read the cache in step 8** and rescans everything (about 7 minutes for 0.38.0), and still writes the cache after the scan; the other rounds use it as usual.
- Every item above has a test in `test_release.py` (unchanged files are skipped and the report is unchanged; a changed content, a changed location, a withdrawn exception, or a changed rule, scanner, Python or Unicode version triggers a rescan; a file with a failure is not cached; an entry with a wrong format is dropped and rescanned; the uploading round does not trust a forged "clean" record; the cache cannot be placed in the output or the repository).

The allowlist allows only reviewed third-party authors, word lists, test data, example paths, build paths in upstream prebuilt files, and binary coincidences.
Each exception pins "rule + SHA-256 of the full printable string", and pins a specific source file path or the SHA-256 of the whole file; nothing is exempted globally by family name. The recorded reasons do not copy private strings into the repository.
A new hit needs its source checked and the allowlist updated by a person; it is forbidden to add a whole new scan report to the allowlist directly.
