The build and packaging entry points are in [`tools/`](tools/README.en.md) in this repository: `tools/build/build-sdk.ps1` and `tools/pubrel/release.ps1` (see [tools/pubrel/README.en.md](tools/pubrel/README.en.md)); the pre-release regression is in [ModAVDE2E](https://github.com/ModAVD/ModAVDE2E).
Local paths (source tree, temp directory, external inputs) are given by arguments or the local config, see "Local configuration" in [tools/README.en.md](tools/README.en.md); the external build method is on the docs site, [Build from source](https://modavd.github.io/en/develop/build).

## Version numbers

The version `0.<N>.<P>` is given with `release.ps1 -Version`: 0 means the internal-test stage; N goes up only when the emulator itself is rebuilt; if the emulator was not rebuilt (only the manager, the capture library, the IME and so on changed, or the package was only repackaged), only P goes up. For example, after 0.40.1, a release that changes only the manager and the capture library is 0.40.2.
From the release after 0.41.0, the manager, the capture library and the IME follow the package ([#216](https://github.com/ModAVD/ModAVD/issues/216)): a component that was repackaged in this release takes this release's version number; one that was not repackaged stays as it is. For example, if 0.42.3 only rebuilt the manager, the manager is 0.42.3 and the capture library is still 0.42.0.
From 0.42.0, the emulator build number is written as the version of the rebuild it belongs to, `0.N.0` (`Pkg.BuildId=0.42.0` in `source.properties`; `build` in `modavd-manifest.json`, in the machine-readable line of the notes and in `changelog.json` is the same string `"0.42.0"`). In speech and in command-line arguments it is called `0.N` (`-Build 0.42`); on disk it is always three parts and changes only when the emulator is rebuilt, so a repackaged 0.42.3 still has `0.42.0` ([#219](https://github.com/ModAVD/ModAVD/issues/219)). Do not write the build number in the notes, the title or PRs.
The manager 0.8.0 shipped with 0.40.0 also demanded at install time that the middle part of the version equal the build number, so 0.40.1 (mas-40, with manager 0.9.0 that no longer requires this match) was released after 0.40.0; only a root folder with 0.40.1 or later installed can use "Update" to install a package whose version and build number differ.
The tag is `v0.<N>.<P>` and the title is `ModAVD 0.<N>.<P>`; the first sentence of the Release notes states which Google AOSP Android Emulator version it is based on and the version of each component in the package.
0.32.1 to 0.40 follow the old rule: N is the build number, P counts the times the package was only repackaged without a rebuild, and the title is `ModAVD mas-<N> (0.<N>.<P>)`.
mas30 and mas32 use the old form `v37.2.10-masN`, which stays as it is and counts as `0.N.0`; `0.32.1` is mas32 repackaged as it was into the new format.

## Release branch

`release/0.<N>` below is by version number (0.41.x is on `release/0.41`), not by build number.

A release is made on a separate branch, apart from development on main ([#175](https://github.com/ModAVD/ModAVD/issues/175)):

- At freeze, this repository, ModAVDManager and ModAVDExtras each cut `release/0.<N>` from main (the same name as in the three source repositories). ModAVDHostIME rarely changes, so it is cut only when it has a change to release. main keeps merging PRs as usual.
- A fix that should go into this release is merged into main first, then a PR cherry-picks it onto `release/0.<N>`.
- A component's release-preparation commit (version, `release/<version>.md`, `release/<version>.SHA256SUMS.txt`) lands on the component's own `release/0.<N>`; each component uses its own version and tag.
- This repository's pinned versions (`tools/pubrel/config/components.SHA256SUMS.txt`, pinning only third-party APKs), the patch series, the manifests and `release/<version>.*` land on this repository's `release/0.<N>`, and the tag is put on the head of this branch.
- Packaging and regression do not wait for the components to be released: `release.ps1` takes the commit at the head of the component's release branch. The output that passes regression is the package that is shipped.
- Publishing goes in order, and stops if a step fails: ModAVDExtras, then ModAVDHostIME (only if it changed), then ModAVDManager, then the three source repositories, then this repository. For each component, first put the tag on the commit recorded in the package, wait until its `release` workflow produces a draft whose attachments and checksum table match, then publish. A component that did not change keeps its old tag.
- A patch release `0.<N>.<P>` continues on `release/0.<N>`.
- After the release, each repository opens a PR that merges `release/0.<N>` back into main.

## Before the release

- [ ] Fix the build number, the committed source to be built, the matching manifest, the patch base and the sources of third-party components. Update the license notices.
- [ ] Preview the build command first, and schedule the real build separately: `pwsh -NoProfile -File tools/build/build-sdk.ps1 -Build 0.42 -WhatIf`. For the real build drop `-WhatIf`; parallelism is at most 16; it stops if the target SDK already exists.
- [ ] Confirm `Pkg.BuildId=0.42.0` in the SDK's `source.properties` (the output directory is `sdk-0.42.0`), and keep the `build-info.json` that the build entry produced.
- [ ] **Run the regression on a test machine**: start/shut down, WHPX, GLES/GuestAngle, MAA/MaaFW shared-memory screenshot and click, existing games and the related fixes; record the results. The runner and the suites are in [ModAVDE2E](https://github.com/ModAVD/ModAVDE2E); run what matches what changed (`-Scope`), and use `-DryRun` first to see which items will run. Keep the result table `results.md` to yourself; it does not go into the Release notes. To shut down an instance as planned, run `adb -P <separate port> -s emulator-<instance port> shell sync` first, then `emu kill`.
- [ ] Do not write "What's changed" or the English "What's new" by hand; collect them from the note files that PRs carry (two lines: Chinese, then English): `pwsh -NoProfile -File tools/pubrel/collect-changelog.ps1 -Build 0.42 -Version <version>` turns each file added to the `changelog.d` of the four repositories since the last release into one Chinese and one English entry, placed first in `tools/pubrel/config/changelog.json` as this release's entry. It also lists commits that carry no note file, so you can check by eye that nothing was missed; if something was, add a file and run it again. For usage see "Release" in [tools/pubrel/README.en.md](tools/pubrel/README.en.md).
- [ ] For a component repackaged in this release, set its version to this release's version, and generate `release/<version>.md` with `release_tools.py component-notes`.
- [ ] After collecting, check the length: `python -I tools/pubrel/release_tools.py notes-budget --build 0.42 [--sdk <SDK root>]` reports the length of the machine-readable line (limit 8000 characters, carrying the changes of up to 10 versions from the top of `changelog.json`) and of the notes above the separator line (limit 4000 characters); it errors when over the limit and warns above 90%. The pre-check of `release.ps1` also checks this, so do not wait until step 7.
- [ ] How to update and known issues do not go into the Release notes: open an issue for a newly found problem and label it `bug`; if this release has something the user has to do (for example, shut down the instances before updating), write it as one "note" with `collect-changelog.ps1 -Note`, and give its English with `-NoteEn`.

## Generate and verify

By default it runs locally only up to the privacy scan. The SDK and the manager package are given by arguments; external inputs such as the source tree, the source base, the notes and the license directory are given by arguments or the local config (see "External inputs" in [tools/pubrel/README.en.md](tools/pubrel/README.en.md)):

```powershell
pwsh -NoProfile -File tools/pubrel/release.ps1 -Build 0.42 -Version <version> -Sdk <SDK root> -Manager <ModAVDManager-version-win-x64.zip> -ImeApk <modavd-ime.apk> -ExtrasDll <modavd_extras.dll> -MumuShim <external_renderer_ipc.dll>
```

`-ImeApk`, `-ExtrasDll` and `-MumuShim` must all be given when packaging: the hash of the host IME APK is pinned in `tools/pubrel/config/components.SHA256SUMS.txt`, and it stops if it is pinned but not given; the capture library and the MuMu compatibility shell are in every package, and it stops if they are not given.

Since 0.39.0 the package contains ModAVDExtras's capture library `extras\modavd_extras.dll` (LGPL-3.0-or-later): `-ExtrasDll` takes the attachment of its Release (before it is released, the one built by CI at the head of the release branch). This repository does not pin its version or hash; like the manager, it is taken automatically at release time: the version is the one written in `CMakeLists.txt` at the head of ModAVDExtras `release/0.<N>` (a tag is used once there is one), and the DLL must match `release/<version>.SHA256SUMS.txt` of that commit, otherwise it stops. A new release of the capture library needs no change in this repository. The MuMu compatibility shell `external_renderer_ipc.dll` from the same ModAVDExtras release is placed as `mumu-shim\shell\sdk\external_renderer_ipc.dll` (`-MumuShim`), for a separately installed MAA: in MAA set the MuMu path to `<ModAVD root folder>\mumu-shim`; it and the capture library must come from the checksum table of the same ModAVDExtras commit, and both must be given together. When the manager and the capture library have no tag yet, the commit at the head of their release branch is used (see "Release branch" above and "When a component has no tag yet" in [tools/pubrel/README.en.md](tools/pubrel/README.en.md)).

1. **Assemble**: following the reviewed file policy, copy the SDK, the desktop APK, the bundled script `modavd-bridge.ps1`, the notes and the licenses, and finally write `modavd-manifest.json` (version, build number, upstream version, platform, minimum AUTO-MAS version, and the size and SHA-256 of every other file). When the SDK file set changes, review the policy first; never delete files from the original SDK.
2. **Main package ZIP**: `ModAVD-0.34.0-win-x64.zip`, with **no outer folder**: the package root is the ModAVD root folder (MirrorChyan compares files by path, and an outer folder carrying the version would make an incremental update equal to a full one). The file name carries the platform, because there may be a `linux-x64` later. Entries use `/`, 7-Zip `-mcu=on`, and Chinese file names carry the UTF-8 flag. After it is done, no single file inside the ZIP is replaced; any change goes through the whole process again.
3. **Verify the main package**: the SHA-256 of every file equals that in the assembled directory, excluded files are not in the package, entries start directly from the package root (an outer folder is an error), all paths and encodings pass, and the manifest corresponds one to one with the files in the package.
4. **Patches**: exported from the commit recorded by the build snapshot, with no co-author trailer in the commit message. A patch from an external contributor keeps their own authorship (GitHub noreply address); a commit that came from upstream by `git cherry-pick -x` (its message has `(cherry picked from commit <40 characters>)` and its author is not the person who committed it locally) keeps the original upstream author; every other author is `qiyinxi <qiyinxi@foxmail.com>`. `scripts/checks.py` accepts only these three, and an upstream author counts only on a commit that has the cherry-pick line. Replay in a separate temporary repository with `git am --keep-cr`; each commit's source tree and author equal the original commit's. Every merged `incoming/<topic>/*.patch` must be in the new series (same patch-id; if it was rebased when taken in, match by author and title); after checking, delete them from the repository (with `git rm`, following the release clone's own line-ending settings; a checkout with `core.autocrlf=true` works too) and put that into the release commit; a topic left for a later release is named with `-KeepIncoming <topic>`.
   The output `patches/series.json` and `patches/BASE.md` are the two files from the release clone plus this release: a series with the same published base and branch head reuses the published directory (the export goes to `work/patches-reused/`, not into `patches/`); the others are new directories, with one entry added at the top of `series.json`, one row added to each of the version table and the directory table of `BASE.md`, and one explanatory sentence under the directory table. The license of a new patch and what it does can only be written by a person, so they are left as "to fill before release", and `checks.py metadata` fails when it sees that. `logs/patch-dirs.json` records which directory each repository uses and whether it is new.
5. **Source archive and manifest**: source files that did not change are reused after their hashes are checked one by one, and only the changed source projects are archived again. `7z a -tzip -mx0 -mcu=on` makes the platform-independent `ModAVD-0.34.0-sources.zip` with an outer folder of the same name; it holds the matching source, `SOURCES.txt`, the two manifests and the `SHA256SUMS.txt` inside the package. The manifests are also synced to `manifests/` in this repository, and are no longer uploaded as separate attachments.
6. **Two checksum tables**: the one inside the package lists only the individual source files and excludes itself; the outer `SHA256SUMS.txt` **lists only two lines, the main package and the source archive**.
7. **Release notes**: the first line is a machine-readable comment (version, build number, upstream version, minimum AUTO-MAS version, and a summary of the changes of up to 10 versions from the top of `changelog.json`); next is the update notice (one line with each component's version, and the changes collected from the note files of the PRs); then a line `<!-- modavd:github-only -->`; below it comes first the English "What's new" (the same opening line and the changes in English), then the byte sizes and SHA-256 of the two ZIPs and the file count and total size of the source archive. The SHA-256 of each source file does not go into the notes; see `<version>.sources.SHA256SUMS.txt` inside the source archive and in `release/` of this repository. The part above the separator line is in Chinese only, is synced to MirrorChyan and shown in AUTO-MAS, is limited to 4000 characters and holds no hashes; the English is below the separator line, shown only on GitHub, and does not count towards the 4000 characters.
8. **Privacy**: the main package, the patches, all source members and the release metadata must all pass, using the general rules of `scripts/privacy.py` plus the private rules kept by the maintainer outside the repository (`-PrivateRules`; it stops if they are not loaded); the general rules also run in the repository CI. A new hit needs its source checked, and the allowlist pins a specific file or content, never allowing a family name globally. The report must be 0 failures. A file that was clean on the last scan and has not changed is skipped according to the local cache (any change of the scanner or the rules rescans everything, and `-NoPrivacyCache` forces a full scan); the round with `-DraftRelease` that really uploads does not read the cache and rescans everything, and still writes the cache after the scan. See "Shared checks and privacy rules" in [tools/pubrel/README.en.md](tools/pubrel/README.en.md).

- [ ] Put the new directories under `patches/` of the output, `BASE.md`, `series.json` (overwrite the ones in the repository; they were made by adding to those two), the manifests and the generated Release notes into the release commit to be reviewed; fill in the "to fill before release" entries in `BASE.md` (file new patches under licenses by the files they change, and say clearly what they add); check the base, the count and the tree in `series.json`.
- [ ] Save `<version>.md`, `<version>.SHA256SUMS.txt` (outer), `<version>.sources.SHA256SUMS.txt` (inside the package) and `<version>.assets.json` (byte sizes and digests) together in `release/`; `<version>` has no `v`, for example `0.34.0.md`. The last one comes from `release-assets.json` that packaging outputs; do not copy numbers by hand from an old release.
- [ ] `checks.py`, `privacy.py` and the allowlist exist only once, in `scripts/`, shared by CI and the release tools. `privacy-private-rules.json` (rules carrying real names, private e-mail addresses, host names and local directories) stays only on the maintainer's machine, outside the repository, and is never committed.
- [ ] The release PR also carries `release/<version>.issues.json` (the issues to close or to add a comment to in this release; write in all that have `0-pending-release`), generated from the release plan with `tools/pubrel/release-pr.ps1 -PlanFile <plan>`; after the review, write a line `Reviewed-Head: <the reviewed head, 40 characters>` in the PR body (the same script with `-BodyFile` generates it). For the format see "Release PR and the two workflows on GitHub" in [tools/pubrel/README.en.md](tools/pubrel/README.en.md).
- [ ] The CI patch replay, consistency and privacy checks all pass. To verify again locally, use the same set of commands in the next section.

## Draft and publish

First publish the components that are new in this release, in the order of "Release branch": the tag goes on the commit recorded in the package (it is in the output of the pre-check, and also in `own` of `snapshot.json` in the output directory); after their Releases are published, create this repository's draft.

Then regenerate with `-DraftRelease` added explicitly and create the draft: it accepts only a package whose components all have tags, the privacy scan does not read the cache and rescans everything, and the draft's tag points at `release/0.<N>`. When a local output already exists you can use `-Force`, which rebuilds only this run's output directory that has a matching ownership mark; on failure the scene is kept.

```powershell
pwsh -NoProfile -File tools/pubrel/release.ps1 -Build 0.42 -Version <version> -Sdk <SDK root> -Force -DraftRelease
```

- [ ] The draft has **exactly three** attachments: the main package ZIP, the source archive ZIP and the outer `SHA256SUMS.txt`.
- [ ] After the draft is made, trigger `gh workflow run verify-release.yml --repo ModAVD/ModAVD -f version=<version>` ([#134](https://github.com/ModAVD/ModAVD/issues/134)): it downloads the attachments on GitHub and checks them against `release/<version>.SHA256SUMS.txt` and `release/<version>.md` of the release commit on `release/0.<N>`, then checks that the reviewed head written in the release PR body and the tree of the merge commit are the same. If it fails, do not publish.
- [ ] **A person looks over the draft before it is published**: the target tag/commit, the version, both checksum tables, the byte sizes and digests of the attachments, the match between the packages and the source, the licenses, the privacy report, the issue links, the upgrade notes and the notice above the separator line are all correct.
- [ ] Publish through the GitHub page after the maintainer confirms; the automatic script only creates the draft, and does not publish or change the repository settings.
- [ ] On publishing, `close-released-issues.yml` runs by itself: following `release/<version>.issues.json` on the commit the tag points at, it checks one by one that the PR that fixes the issue is in this release, closes the ones that pass (or adds a comment), adds the release link and removes `0-pending-release`; the ones that fail keep their label and are listed in the job summary. Look at the summary; after a failure is fixed, run `gh workflow run close-released-issues.yml --repo ModAVD/ModAVD -f version=<version>` again, which does only what is still not done. `release: published` uses the workflow file on the commit the tag points at, so `close-released-issues.yml` must be on the release branch (step 1 of the release script checks this); if it is not, the only way is to run the command above by hand after publishing.
- [ ] The `release/0.<N>`, the tag and the default branch of the three source repositories are still pushed from the maintainer's machine for now (it needs credentials that can write across repositories, which are not in CI).
- [ ] To change the notes after publishing (for example, adding a known issue), edit the Release directly; do not delete the separator line or the machine-readable comment on the first line.

## Run the same checks as CI locally

Run in the root of this repository; you need Python 3.12, Git and a network connection to AOSP. `<fresh temp directory>` must not exist yet.

```powershell
python scripts/checks.py patches --work <fresh temp directory>
python scripts/checks.py metadata
python scripts/privacy.py .
python -I tools/pubrel/test_release.py --work <fresh temp directory>
python -I tools/pubrel/test_release_ci.py
```

The last two are the unit tests of the release tools' failure paths and of the checking logic of the two release workflows (check the draft, close issues); they also run in CI. If you changed `tools/pubrel/` or `scripts/`, run them locally first.
The maintainer also runs `python scripts/privacy.py . --private-rules <private rules outside the repository>` to scan with the private rules.

The patch check shallow-fetches the public base from `android.googlesource.com` according to `BASE.md` / `series.json`, and does not depend on the maintainer's object store.
The CI used for the checks has read-only repository permission and a checkout action pinned to a commit, and needs no secret. The two release workflows also use only `GITHUB_TOKEN`: the job of `verify-release.yml` that downloads the draft needs `contents: write` (a draft is visible only to a token that can write), does not check out or run code from the repository, and its checking job is read-only; `close-released-issues.yml` has only `issues: write` and everything else read-only.
